# Projektor 構成設計

採用：2026-10-12。ユーザー指定により、以下をProjektor修正の最上位の設計制約とする。既存実装・既存API契約・過去の計画・既存テストと衝突した場合は本仕様を優先する。実装互換性を理由に本仕様を弱めない。ユーザーの業務データ・履歴・識別子の保持と、セキュリティ変更に必要な承認は別途維持する。

設計対象：人と個別のAgentが同じ仕事・Wikiを扱い、認証切れ、通信断、再起動、同時編集を経ても継続できるシステム。既存コードの配置やテスト件数を設計の根拠にしない。本書は設計であり、実装完了・本番変更の報告ではない。

## 1. 結論

**一つのAPI、一つの業務DB、一つの配備単位。内部は業務の所有者で分け、外部依存を境界に置く。**

WebとAgentは同じ業務APIを使う。RESTとMCPは同じユースケースに接続する。バックエンドの業務モジュールは以下の三つとする。

| モジュール | 所有する状態と判断 | 所有しないもの |
|---|---|---|
| Identity | 主体、資格、セッション、所属、権限、設定権、取消と監査 | Issueの状態遷移、業務内容、Agentの実行状態 |
| Work | Project/Workspace、Issue、Wiki、コメント、予定、参照、改訂・変更履歴 | 資格検証、実行lease、外部処理の再実行判断 |
| Execution | 試行、実行権、lease、進捗・結果、中断・再開の記録 | Issueの解決判断、外部処理そのものの実行 |

操作記録・一括確定・結果照会は共通の永続化機構であり、第四の業務モジュールにしない。移行と配備は運用ツールとして通常の業務経路から分ける。

この単位を選ぶ理由は、権限・業務更新・履歴・操作結果を同時に確定する必要があるため。独立サービスへ分割すると、この要件に対して分散トランザクションと通信障害処理が増える。三つの所有者は同一プロセス内の境界で十分である。

## 2. ソースと依存の構造

各業務モジュール内は必要な三責務に分ける。

- **規則**：入力の意味、変更可能項目、必要権限、状態遷移、期限の比較。型付きデータを受け、判断を返す。通信、DB、時計の直接取得を行わない。
- **ユースケース**：規則を適用し、必要な照会・一括確定を呼び、結果を返す。保存に必要な契約をここで定義する。
- **保存アダプター**：その契約をD1で実現する。SQL、現在権限の再確認、競合検出、一括更新、履歴、操作記録を担当する。

依存方向は、入口→ユースケース→規則・契約。D1などの具体実装→契約。起動時の組立箇所だけが両者を接続する。ユースケースからD1実装をimportしない。外部認証の検証器も同様に注入する。

単純な関数・型で構成する。汎用repository、任意SQLのDSL、プラグイン登録、全操作共通の巨大なUnit of Workは作らない。型・層・ファイルを増やすこと自体を目的にしない。

リポジトリの大区分は、apps（入口と組立）、modules（上記の業務規則・ユースケース・契約）、adapters（D1・外部認証・資格保管）、web（画面とクライアント状態）、agent（APIクライアント）、migrations、deploy、testsとする。各ソースに所有モジュールと内部の役割を示し、複数責務のソースを分割する。公開入口を通さない参照は検査で拒否する。

## 3. 保存契約：get/saveでは足りない

業務の操作をそのまま表す限定的な契約を置く。

- Work：Issue/Contentの作成・変更、一覧・詳細・履歴、操作結果の照会
- Execution：acquire、renew、report、interrupt、reconcile、restart
- Identity：authenticate-and-touch、commit-login-if-current、redeem-once、grant/revoke、issue-setup-if-current

変更には操作ID、対象、期待revision、型付きの変更内容を渡す。Executionでは該当操作に必要なattempt/leaseの識別子も渡す。主体と資格は検証済みの要求コンテキストへ結び付け、呼出し側の本文から指定させない。任意SQLや任意callbackを契約に渡さない。

結果は「操作が適用されたか」と「要求が失敗した理由」を別に表す。適用状態は確定済み／非適用が証明された／不明。失敗理由は入力不正・認証失効・権限拒否・競合・入力不一致・利用不能など。確定済みには新規確定と既存結果の回収を区別する。更新後の権限拒否は、理由が権限拒否でも適用状態は不明である。保護された現在値を含められるのは、その読取り時にも認可が成立する場合だけ。単なる例外・404・401・タイムアウトを「未実行」の証明にしない。非適用証明はその試行だけを対象とし、同じ操作IDの並行試行が存在しないとは証明しない。

結果開示の許可／拒否も適用状態とは別である。確定後に失権した場合は、サーバーには確定記録を残すが、外向けには認可エラーと要求側が既に持つ操作IDだけを返す。保存結果・本文・存在確認情報を漏らさず、クライアントは適用不明として保持する。

代表的な境界契約は次のとおり。revisionは現在のwire表現を維持し、意味は期待版とする。

| 操作 | 契約への入力 | 原子的に検査する条件 |
|---|---|---|
| Issue変更 | projectId、issueId、operationId、revision、型付きpatch | 現在資格・必要権限、対象revision、判定に用いた関連対象の版または整合条件 |
| 実行更新 | projectId、issueId、operationId、attemptId、leaseVersion、型付きaction | 現在資格・実行権限・担当、現在試行、期待版、DB時刻でのlease有効性 |
| 権限変更 | operationId、対象主体・範囲、対象revision、型付きgrant/revoke | 実行者の現在管理権限、対象の期待版、変更範囲の上限 |
| 設定権の消費 | operationId、設定権証明、設定する資格の検証済み値 | 設定権の有効期限・未消費・対象version、必要な本人binding |

返却は型付きsnapshot付きの確定receipt、認可された競合情報、または失敗理由と適用確度で表す。読取りは値／拒否／不存在／利用不能、結果照会は確定結果／未発見／拒否／利用不能を区別する。

既存wire DTOと業務型が同じ意味なら共有する。業務APIをunknown入力・汎用JSON出力だけにしない。unknownは外部データを検証する入口に限定し、移行元metadataなど本当に可変なデータだけJSONを許す。

## 4. 更新の一周

1. 入口で資格の形式、要求サイズ、Origin/CSRFなどプロトコル上の条件を検査する。
2. Identityがアプリ内の主体を確定する。ここでの成功は、後続更新の認可確定ではない。
3. ユースケースが型付きの変更要求を検証し、必要な操作を保存契約へ渡す。不要な事前読取りは追加しない。
4. D1アダプターが、現在の資格・主体・所属・権限・対象の版・必要な業務条件を更新と同じトランザクションで検査する。
5. 業務データ、revision、履歴、操作結果を一体で確定する。どれかが失敗すれば全体を確定しない。
6. 応答する結果にも現在の読取り権限を適用する。認可付きの結果SELECT時点で権限を失っていた場合、以前読めた本文を成功応答として返さない。既に送信した情報を後の取消で回収できるとは保証しない。

状態依存の判断が必要な操作では、認可済みsnapshotを読み、純粋な規則が変更意図と期待状態を決める。アダプターはその判断に使った対象・関連状態のrevisionまたは具体的整合条件が今も成立することを一括確定時に検査する。主対象のrevisionだけで、別に変更可能な担当・参照先まで保護できるとは扱わない。食い違えば競合として戻し、勝手に最新状態へ適用し直さない。期限は確定時のDB時刻で再検査する。

必要権限を決める規則は業務側の一か所に置く。保存時のSQL判定と直接操作・保存済み操作の再取得で別々の権限表を持たない。SQLによる現在状態の検証を、古い事前認可のbooleanで置き換えない。

## 5. 結果不明からの回復

人の未保存入力は同一ブラウザ内に保持する。Agentの準備済み操作は、実行前にサーバーへ主体付きで永続化し、現在権限に基づく一覧とID指定の取得で再発見できるようにする。別executorでの再開はこの発見経路から始める。クライアントのローカル記録は迅速な復旧用であり、Agentの準備済み操作を発見する唯一の保存先にしない。

送信前に、クライアントが主体・対象・操作ID・変更内容を保存する。復旧に必要な記録を保存できなければ、その保証を必要とする書込みは送信しない。

保存済みの将来形式については、現在権限の下で認識可能な対象・結果を照会できても、新しい実行は対応形式でなければ拒否する。既に確定した正規の結果の回収と、未確定操作の実行可否を別に扱う。

サーバーは主体と操作IDに対して入力の同一性と確定結果を保持する。同じID・異なる内容を拒否する。準備済みの操作を実行する場合は、その保存済み入力と実行内容の一致を更新時にも検証する。

準備登録の応答が消失してIDをローカルから復元できない場合も、同じ主体の保存済み操作を発見して入力と対象を照合する。未処理候補が複数ある場合は推測で選んで実行せず、状態を提示して解決する。サーバーにも永続保管にも一度も到達していない入力までは復元保証しない。

応答消失後は、同じ主体として再認証し、同じIDの結果を先に照会する。確定結果があれば回収する。権限拒否・結果欠如・結果不明を区別し、新しいIDで自動的にやり直さない。再送は契約上安全な同一操作だけとし、設定権の発行や外部処理を勝手に再実行しない。

DB内の重複防止は、Agentが外部で行う操作の一回限り実行を保証しない。外部操作の中断はExecutionのreconcileで反映と成果物を確認し、その結果を残してから新しい試行へ進む。

## 6. 認証と継続利用

四つの責任を混ぜない。

1. **外部本人確認**：署名・issuer・audience・期限・鍵取得など。正規化された本人確認結果だけをIdentityへ渡す。プロバイダーの診断情報はこのアダプター内で扱う。
2. **アプリIdentity**：外部主体との既存対応、アプリ主体の有効性、セッション、資格、所属と権限を管理する。外部認証成功だけで参加・管理権限を自動付与しない。
3. **操作時の認可**：読取りと更新確定の時点で現在権限を適用する。資格取消・主体無効化・権限変更が既存接続にも反映される。
4. **クライアントの資格保持**：人はHTTPSのHttpOnly/Secure Cookie、Agentは実行環境から提供される安全な資格providerを使う。業務コードは特定VM・ファイルパス・常駐プロセスに依存しない。秘密を下書きやログへ保存しない。

**初回設定の経路**：設定権を発行したPOSTの応答だけに、回復不能な秘密を置かない。発行前のcontext取得でブラウザの保護されたbindingを確立し、その証明・本人・操作IDへ一つの設定処理を結び付ける。発行応答が失われても、同じ証明と操作IDで設定状態を再取得し、同じ設定処理へ戻れる契約にする。設定権を消費するのはパスワード設定の原子的な完了時である。新しい設定権を自動発行して帳尻を合わせない。bindingまで失った場合は自動復帰の対象外とし、既存の権限を持つ管理者による明示的な取消・再設定手順へ移る。本人名や操作IDだけでgrantを取得する経路、未設計のbinding付け替えAPIは作らない。これは現行のハッシュだけを保存する一度きり秘密応答に依存した経路からの変更点として扱う。

設定contextはサーバー生成の十分な乱数から作り、ブラウザが値を指定・持込みできないようにする。host-onlyのSecure/HttpOnly Cookieを使い、context作成・発行・完了は正確なOriginとCSRFを検査する。contextの秘密をURL、JS保存領域、ログへ出さない。一度bindingされたcontextを別の主体・操作ID・対象へ付け替えず、別入力の再送は競合とする。

設定を再開する権限は、この事前に確立した短時間のcontext capabilityと操作IDで表す。サーバーはそのハッシュから同じgrantを解決し、失われたbearer secretの復元・再発行を必要としない。有効期限はcontextの絶対期限、bootstrapの締切、発行時の外部本人確認の期限、設定権の期限の最短値とし、状態照会や再送で延長しない。失効後は完了処理を許可しない。通常業務の30/90日セッションとは別の、初期設定専用の権限である。完了結果の回収は、同じ操作のreceiptに保存したcompletedAuthVersionと現在の主体版が一致し、主体が有効で、contextが未失効・未取消の場合だけ、非秘密の完了状態を返す読み取り専用経路とする。後のresetや主体無効化では開示を拒否する。設定権を再使用しない。

ログインでは実／dummy hashの検証後、現在のpassword版・主体版・challengeを同じ確定処理で再確認してセッションを作る。パスワード変更は設定権消費・主体版更新・旧セッション無効化・監査を一体で行う。Agentのブラウザ引換えは短時間・一度きり・元資格の範囲内とし、元資格の取消や期限が派生セッションにも反映される。

セッション正本はサーバー側の永続状態であり、Worker再起動で失わない。人の無操作30日・絶対90日の既存要求と、Agentが人の毎日の再ログインなしで使える要求を、クライアントと前段を含む全経路で満たす必要がある。

**認証入口の設計推奨**：通常業務の認証はアプリIdentityに一本化し、Cloudflare Accessのブラウザセッションを全業務要求の必須条件にしない。Cloudflareのホスティング・TLS・通信防御は維持する。Accessは必要な外部本人確認や限定的な初期管理入口に使い、業務権限は付与しない。これは無認証公開ではなく、業務API自身が全要求を認証・認可する構成である。

選択理由は、保存済み設定のAccess 24hとアプリ30/90日を二重の必須期限にすると、前段資格の更新可否が別の継続条件となり、アプリの期限だけでは要求を保証できないため。Agentにも人のブラウザ認証を要求しない。前段依存を外す前に、全経路のアプリ認可、ログインの試行制限、パスワード保護、CSRF、セッション失効、監査を検証しなければならない。認証なしで業務DBへ到達できる別経路を作らない。

入口を、公開静的ファイル・非秘密の認証context、認証必須の業務HTTP/MCP、制限されたowner bootstrapに分類する。業務経路は別hostnameや直接入口でも同じアプリ認可を適用する。Cloudflare風のヘッダー名やproxy通過を本人確認として信用せず、外部assertionを採用する入口では署名等を検証する。Agentの通常API認証は個別のアプリ資格を主経路とし、任意の前段admissionを隠れた必須条件にしない。

この推奨は、既存資料の「Accessを通常入口に維持する」方針とは差がある。ユーザーはこの仕様を優先する修正を指定した。本番の認証設定変更そのものの実行承認・実施とは区別する。

## 7. WebとAgentの状態

サーバーが保存済み業務状態の正本を持つ。Webは表示条件、未保存入力、送信中操作を所有する。本人・対象・版・操作IDに結び付けて保持し、主体切替時は旧主体の表示と遅延応答を遮断する。同じ本人でも現在権限を確認して復元する。

Agent SDKは資格取得、API呼出し、操作記録と結果照会を担当する。Cloudflareヘッダー生成やファイル読取りは任意の外部アダプターであり、SDKの必須依存にしない。保管providerの抽象化と、実在する永続保管・更新運用の確認を混同しない。

## 8. 検証とリファクタリング順序

設計の境界・契約・上記の経路を確定してから実装する。

1. 要求から、維持するwire契約と、要求違反として変更する挙動を識別する。既存挙動を無条件の正解として固定しない。
2. 純粋な業務規則を抽出する。
3. 型付き保存契約を定義し、既存の原子的SQLをその実装へ閉じ込める。
4. ユースケースを契約だけに依存させ、HTTP/MCPを同じユースケースへ接続する。
5. 業務単体はDBなしで検証する。実D1では取消競合・古い版・途中失敗・重複・期限を検証する。実ブラウザでは入力保持・主体切替・認証復帰を検証する。
6. 対応するソース版と証拠を記録する。実接続・実資格保持・前段認証・実端末の未確認を、ローカル試験で合格に置き換えない。

静的検査は責務の正しさを証明しない。禁止依存を防ぐ補助として使う。実装をラッパーで包んだだけの状態や、設計上未決の認証経路を残した状態を完成扱いしない。
