# Integrations (step 12)

Integrations owns external references, feedback intake, source configuration and outbound delivery state. The owner DAG adds only Platform, Access, Projects, Issues and Wiki. References store target IDs locally; Issues and Wiki storage is unchanged. Authorization for target operations is checked through their public APIs. Feedback inbox reads filter entries by live project visibility; source and delivery administration require an owner/admin human.

`POST /integrations/feedback/{workspaceId}/{sourceId}` accepts at most 32 KiB of UTF-8 JSON with `title` and `body`. Send `x-projektor-timestamp` (Unix seconds), `x-projektor-delivery-id`, and `x-projektor-signature` (lowercase hex HMAC-SHA256 of `${timestamp}.${deliveryId}.${rawBody}`). The five-minute window is checked against the Worker clock. The `FEEDBACK_LIMIT` binding limits requests per workspace/source. A unique `(workspace_id,source_id,delivery_id)` key makes duplicate submissions return the existing ID. The signature includes delivery ID, so copying a valid signature to a new delivery ID is rejected.

Source creation returns the inbound secret once. A Worker secret binding `INTEGRATIONS_KEY` (64 lowercase hex characters representing 32 random bytes) reaches Integrations only through `createSecretVault`; Integrations stores the derived inbound secret hash. HKDF-SHA256 derives independent HMAC and AES-256-GCM keys using salt `projektor:integrations:v1` and purpose labels `inbound-hmac` / `outbound-aes-gcm`. Outbound webhook registration returns a separate random secret once and stores AES-GCM ciphertext with a fresh IV. The key must remain available for existing sources and deliveries: losing or replacing it invalidates inbound signatures and outbound decryption. [Cloudflare documents required secret bindings](https://developers.cloudflare.com/workers/configuration/secrets/); provision the binding in the approved environment before enabling Integrations. An absent or malformed key disables only Integrations: its REST routes return HTTP 503 with `unavailable`, MCP tools return the same PlatformError code, and the Integrations scheduled drain is skipped. Other modules and scheduled consumers remain available. The repository has no secret value or production resource ID.

`deliverWebhook` is a module API command and is not exposed as a Gateway operation. It queues one delivery per source and external ID for a subscribed event type. Composition wraps the native Worker fetch function so the send port preserves its required receiver. The hourly scheduled handler signs `${timestamp}.${body}`, sends HTTPS POST with `redirect: "manual"`; every 3xx is a failed attempt, and retries at 30, 60, 120 and 240 seconds before marking the fifth attempt failed. URL validation rejects IP literals, localhost, common private/internal host suffixes and detected Cloudflare-internal names. **Known limitation: DNS rebinding.** Hostname checks do not resolve or pin destination IPs; DNS resolution after validation can change to a private address. Redirect rejection does not close this gap; production outbound egress policy or a DNS-pinning service is needed if webhook destinations are allowed outside a controlled set.

Feedback conversion uses `int_convert_<feedbackId>` as the Issues operation ID and `int_<feedbackId>` as the issue ID. If Issues commits but Integrations does not, retry calls Issues with the same IDs and finishes the feedback CAS. `integrations_receipts` prevents a changed payload under an operation ID. `integrations_guards` aborts stale CAS batches. The owner tables are `integrations_links`, `integrations_sources`, `integrations_feedback`, `integrations_deliveries`, `integrations_receipts`, `integrations_guards`, `integrations_history`, and `integrations_events`.

Step 12a audit adds no business commands, queries, events, tables or owner edges.
`integrations.sources`, `integrations.source.register`, `integrations.webhook.register`
and `integrations.deliveries` are REST-only administration; MCP neither lists nor
invokes them. `deliverWebhook` remains a composition/module API only.

The HKDF key schedule replaces Step 12's direct master-key reuse. Existing source
hashes and outbound ciphertext created with that pre-audit implementation are
incompatible and require new sources (new IDs) and webhook registration; there is no silent legacy
fallback. This change precedes production activation, changes no stored rows, and
does not claim an automated data migration. See [the audit](test-audit.md#integrations-independent-test-audit--12a)
for executed probes and remaining limits.
